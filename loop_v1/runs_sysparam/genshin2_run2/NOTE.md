# 关于这份证据的两点交代

## 1. `snap_before.txt` 被误删, 不是丢了而是被污染后主动删掉的

编排脚本的重试外壳有个 bug: `autoloop.py` 在「收尾快照与进入前不一致」时正常返回
退出码 1, 而外壳把非零退出当成「没拿到锁, 再试一次」, 于是在本轮 13:05 正常跑完之后
又自动起了第三轮。第三轮在探测阶段 (13:05–13:07) 就被我掐断, **没有产生任何候选数据**,
但它把本轮的 `snap_before.txt` 与两张启动截图覆盖掉了。

与其把第三轮的文件冒充成本轮的, 不如删掉并写清楚。本轮的进出快照比对结论本身没丢
—— `report.json` 里的 `final_snapshot_diff` 是本轮自己的两张快照算出来的, 逐候选的
`gen1/cand*/snap_before.txt` / `snap_after.txt` 也都是本轮原件, 未被触碰。

根因已修: 收尾的留痕判据改成「本场所有候选写过的项的并集」, 与逐候选判据同一套口径;
环境自己动的项 (厂商管家改的 `cpu.policyN.scaling_max` 等) 不再让整场退出码变成 1。

## 2. 三轮的关系

- `genshin2_run1/` — 第一轮 (12:25 结束)。跑在「留痕判据按写死名单」的旧代码上,
  cand1 因此被误判成留痕。cand3 是本闭环**第一个走完全程统计判定**的候选。
- `genshin2_run2/` — 本目录, 第二轮 (13:05 结束)。跑在修好的代码上,
  cand1 完整跑完 5 对并给出判定。
- 第三轮 — 误启动, 探测阶段即掐断, 无数据, 不入库。
