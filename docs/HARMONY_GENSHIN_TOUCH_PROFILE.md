# 鸿蒙原生《原神》触控回放记录

这是一份针对游戏和画面布局的输入说明。已在华为 nova 16、HarmonyOS 6.1.0.130、原生《原神》`com.miHoYo.Yuanshen`、横屏 2520 × 1152 上实测。它用于证明无 root 的 HDC 可以驱动游戏并同步采集指标；目前不是用于比较优化前后的标准轨迹。

## 起点和界面检查

1. 用 DevEco Studio 附带的 `hdc list targets` 确认设备已授权。在宿主终端确保 `hdc` 在 `PATH`；`phonefarm` 的 HDC 后端调用的是命令名 `hdc`。
2. 手动进入蒙德城开放世界，退出派蒙菜单、地图、对话框、活动弹窗和背包。保持角色在城门内道路、面向市集；确认左下虚拟摇杆与右侧跳跃键均可见。
3. 确认屏幕为 2520 × 1152 横屏。窗口缩放、云游戏画面、系统悬浮窗或游戏 UI 布局改变后，先重测坐标。不要把这份表直接套到其他设备。
4. 记录角色、画质档位、游戏帧率上限、天气/昼夜、网络状态、供电状态、起点画面。当前脚本不会自动把角色和镜头送回同一像素位置，重复轮次只用于输入冒烟。

## 坐标与动作

坐标原点是整屏左上角，单位为物理像素。百分比用于分辨率变化时寻找初始候选，仍需按游戏 UI 实测校准。

| 触点 | 起点 | 终点或点击 | 屏幕比例约值 | 游戏作用 | 实测状态 |
| --- | --- | --- | --- | --- | --- |
| 左拇指虚拟摇杆 | (400, 850) | (400, 700) | 起点 (15.9%, 73.8%) | 向前走 | 已观察角色位移 |
| 左拇指虚拟摇杆 | (400, 850) | (400, 1000) | 终点 (15.9%, 86.8%) | 向后走 | 已观察角色回退 |
| 右手视角区 | (1300, 650) | (1450, 650) | 起点 (51.6%, 56.4%) | 视角向右转 | 已观察画面转动 |
| 右手视角区 | (1450, 650) | (1300, 650) | 终点 (51.6%, 56.4%) | 视角向左转 | 已观察画面回转 |
| 跳跃键 | — | (2210, 790) | (87.7%, 68.6%) | 点击跳跃 | HDC 返回点击成功；未建立逐帧动作断言 |

双指手势的两个起点和终点按“左起、左终、右起、右终”排列。每条 `uinput` 命令会完整按下、移动、抬起；两条命令之间不会保留手指按下状态。`-k 300` 是移动后继续保持 300 ms，最后的 `600` 是移动用时 600 ms。OpenHarmony 命令行最多支持三指同时移动。单独 `uinput -T -c` 可点击 UI，但按钮位置会随游戏和界面状态变化。

## 已运行的短场景

脚本在 [`examples/harmony_genshin_town_loop.json`](../examples/harmony_genshin_town_loop.json)：

1. 左手向前、右手向右，双指同时移动。
2. 左手向后、右手向左，双指同时移动。
3. 点击跳跃；保留短暂等待供截图。

从仓库根目录执行（本机 HDC 安装路径）：

```sh
export PATH="/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains:$PATH"
(cd src && cargo build --release)
codesign --force --sign - src/target/release/phonefarm
src/target/release/phonefarm script \
  --task harmony_genshin_touch_probe \
  --serial hdc:<connect-key> \
  --settle-ms 100 \
  examples/harmony_genshin_town_loop.json
```

`phonefarm script` 在每一步动作前截屏，当前 5 步脚本应产生 `step1.jpg` 到 `step5.jpg`。检查 `step1` 与 `step3` 的背景方位变化、`step5` 的角色动作，以及 `log.jsonl` 里的动作顺序。如果截图缺失，或前台变成菜单、对话、死亡/传送画面，则该轮输入测试无效。脚本的 `achieved=true` 只表示执行器走完步骤，不能单独证明游戏接受了动作；HDC 不在 `PATH` 时曾出现过假完成。

2026-09-24 的真机联跑使用两轮脚本和 26 次 HiSmartPerf 采样，得到 10/10 张非空步骤截图。人工检查 `step1`、`step3`、`step5`、`step6`、`step10`：画面维持在原生《原神》开放世界，前进/视角变化可见，两轮末尾都拍到了跳跃动作。这证明此设备上的短场景输入与指标采集可串起来，但不证明跨轮位置精确归位。

同一天再做了两次独立联跑，共三轮。每轮都是 26 个样本、两次 5 步脚本和 10/10 张截图，三轮都被标记为放电。按三轮摘要值计算的样本标准差除以均值（CV）：FPS 0.15%、全窗口 p95 帧时 0.13%、估算功耗 0.71%。这只是**初步复测**：三轮的角色位置和视角并不完全相同，约 30 FPS 的游戏上限也会压低 FPS 波动；不能把这些 CV 当作固定场景优化 A/B 的可重复性门槛。

## 供电与功耗

这台零售机上 `phonefarm perf --suspend-charging` 未能停充：设备 shell 没有 `su`，相关电源节点也不能由普通 HDC shell 写入。USB 连接时测试仍可采 FPS、帧时和温度，但不能把 USB 供电下的电流读数当作整机放电功耗。

需要测电池放电功耗时，先通过 USB 启用无线 HDC，再让 Mac 与手机保持在同一局域网，拔掉 USB 线。确认无线 target 仍在线，并用 `hidumper -s BatteryService -a -i` 检查 `chargingStatus=0`、`pluggedType=0`、`nowCurrent<0`；任一条件不满足就丢弃该轮功耗。无线连接偶发断开时先重新 `hdc tconn <手机IP>:<端口>`，再做完整预检。2026-09-24 的 26 样本游戏联跑在放电状态下得到约 2.48 W 平均功耗；这只是该场景的观测值，没有可比较的优化候选。

## 变成可重复评测前还缺什么

- **轨迹归位**：选择可自动导航的固定起点，控制角色与镜头朝向，并在每轮开始和结束做画面锚点匹配。当前前后手势的移动量不保证严格抵消。
- **按键覆盖**：菜单、战斗、技能、冲刺、交互的坐标表必须逐游戏逐 UI 状态验证，不能把本文件的开放世界坐标推广到全游戏。
- **输入验收**：检查目标游戏仍在前台、HUD 存在、关键帧确实变化，并把失败写成失败结果。将来要记录每条命令退出状态和完整 stdout，而不是只看 `script` 的结束摘要。
- **采集同步**：在脚本活动窗口同步采 `SP_daemon` 的 FPS、`fpsJitters`、温度和 CPU/GPU 指标；保存原始 `data.csv`、脚本日志和截图。USB 供电时电流不能当整机放电功耗。
- **统计**：锁定游戏画质和帧率上限、起点与采样窗口后，才进行多轮 p95 波动、A/B 交替和显著性检验。当前短场景的数据不能证明优化收益。

此路径不创建系统可识别的虚拟手柄，也不修改《原神》安装包或渲染管线。
