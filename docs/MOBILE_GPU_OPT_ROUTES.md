# 移动 GPU 优化技术路线梳理

> 状态: 初版 · 2026-09-21 · 对应 2026-09-10 群内「移动 GPU 上可以做的优化技术路线可以先梳理一下」
> 立场: **harness 既是评估性能 gap 的框架, 也是优化性能的 loop**。本文是这个 loop 的候选改动清单。
> NN (超分 / 插帧) 是清单里的一类候选, 不是主线 —— 它和其它每一条一样, 都要走同一套基线→改动→对照→判定。
> 实测数据来源: 红魔 NX809J (Android 16 / 骁龙 SM8850 / Adreno 840v2 / Magisk root), 原神国服 7.0.0,
> `loop_v1/runs/report.json` 与 `src/bench.rs`。

---

## 0. 这份文档回答什么

三个问题:

1. 移动 GPU 上**有哪些**优化手段, 各自能吃到多大的量级;
2. 每一条**在 loop_v1 里怎么验** —— 不能被这套闭环验证的路线, 不进候选;
3. 哪些路线需要**白盒**(游戏源码 / 引擎 hook), 哪些黑盒就能做。

第 3 点是分叉点, 它决定后面所有工作量的去向, 建议先在群里钉死。

---

## 1. 为什么不能照搬 PC 的经验

移动 GPU 和 PC GPU 有三条结构性差异, 下面整张清单的"移动端特有性"一列都来自它们:

| # | 差异 | 后果 |
|---|---|---|
| 1 | **TBDR 而非 IMR**。屏幕切成 tile, 每个 tile 的颜色/深度留在片上 tile memory | PC 上进 DRAM 是正常的, 照搬到移动就是灾难。反过来, 移动上有一批 PC 根本没有的免费优化 (subpass 合并、tile 内 resolve) |
| 2 | **多一遍 binning**。所有顶点位置要先读一遍并写 tile list | 顶点属性带宽在移动上被读两次; PC 完全没有这一遍 |
| 3 | **带宽 / FLOPS 比远低于 PC, 且共享 LPDDR**。CPU / GPU / NPU / ISP 抢同一条总线, 上面还压着热预算 | 移动端真正的瓶颈通常是**搬数据**和**热**, 不是算力。PC 上"多算一点换少存一点"的交易在移动上经常反过来 |

**本机实测的佐证**: 把 DDR/LLCC 总线下限钉到硬件上限 (3187 → 5333 MHz, +67% 带宽),
帧时间 p95 显著改善 −0.586 ms (−1.61%, p = 0.0079), 但 `gpu_active_mean` 变化**不显著** (p = 0.42)。
即: 该负载下 GPU 的计算并没有被带宽饿着, 收益来自别处 (推测为总线升频的响应延迟)。
这条数据说明**"带宽不够"不能当成默认假设, 要一条条量**。

## 2. 路线清单

量级一列是通用经验值, 不是本机实测; 本机实测只在明确标注处。
"怎么验"一列全部映射到 `loop_v1/` 现有的工具链。

### A. 带宽 / Tile Memory —— 移动第一大头

| 路线 | 移动端特有性 | 量级 | 在 loop_v1 里怎么验 | 前提 |
|---|---|---|---|---|
| **Render pass 合并**, G-buffer 留在 tile memory (Vulkan subpass / `framebuffer fetch` / PLS) | PC 是 IMR, 没有 tile memory, deferred 走 DRAM 属正常 | 1080p 4×RGBA8 G-buffer ≈ 33 MB/帧的读+写全省 | 主指标 `frame_p95` + `bw_median` 总线投票 | **白盒** |
| **LoadOp / StoreOp 正确性** (`DONT_CARE` vs `LOAD`) | PC 上无所谓 | 一个多余的 `LOAD` = 整帧读带宽。最典型的免费的钱 | 同上, 差异应直接反映在总线投票上 | **白盒** |
| **MSAA 在 tile 内 resolve** | 移动 4×MSAA 近乎免费; PC 上是实打实的带宽 | 高 | `frame_p95` + `gpu_active_mean` | **白盒** |
| **ASTC + mip 完整性** | 无 mip 的纹理在缩小时 cache miss 爆炸 | 中高 | 资产级改动, 需重新打包 | **白盒** |
| **UBWC (高通) 命中率** | PC 无对应概念; 某些格式或 CPU 读会强制解压 | 中高 | kgsl 事件里的带宽投票 | 白盒为主 |
| **半分辨率 bloom / SSAO / 粒子, 降 RT 精度** | 移动带宽/FLOPS 比远低于 PC | 中 | `gpu_active_mean` 应明显下降 | **白盒** |
| **Overdraw / 半透明粒子控制** | 移动头号带宽杀手 | 高 | `gpu_active_mean` + `frame_p95` | **白盒** |
| **系统侧总线 DCVS 下限** | 厂商默认策略偏省电 | **本机实测: p95 −1.61%** | 已验证, `knob_ddr_boost.sh` | **黑盒可做** ✅ |

### B. 几何 / Binning —— 移动独有的一遍

| 路线 | 移动端特有性 | 量级 | 在 loop_v1 里怎么验 | 前提 |
|---|---|---|---|---|
| **顶点流分离** (position-only stream) + 属性压缩 (half / snorm / 10-10-10-2) | binning pass 要把所有顶点位置读一遍。**PC 没有这一遍** | 中高 | `gpu_active_mean` | **白盒** |
| Draw call 合并 / instancing / GPU-driven indirect | 移动驱动的 CPU 开销显著高于 PC | 中 | 帧间隔的 CPU 侧分量 (`queue_p50`, 本机 4.37 ms / 13.05%) | **白盒** |
| 小三角形剔除 / LOD | 小三角形在 TBDR 上按 tile 重复处理 | 中 | `gpu_active_mean` | **白盒** |

### C. Shader

| 路线 | 移动端特有性 | 量级 | 在 loop_v1 里怎么验 | 前提 |
|---|---|---|---|---|
| **FP16 / mediump** | Adreno / Mali 上 fp16 是真 2× ALU 吞吐 + 半寄存器压力。PC GPU 通常同速。**移动独有的大杠杆, 且改动局部** | 高 | `gpu_active_mean` | **白盒** |
| 避免 `discard` / alpha-test | 破坏 Adreno LRZ、PowerVR HSR 的 early-Z。PC 上代价小得多 | 中高 | 同上 | **白盒** |
| 寄存器压力 → occupancy | 移动寄存器堆更小, 更敏感 | 中 | 同上 | **白盒** |
| Shader 变体 / PSO 预热 | 移动编译更慢, 首次卡顿更明显 | 中 (只影响长尾) | `frame_p99` 与首帧 | **白盒** |

### D. 分辨率 / 上采样 / 重建

| 路线 | 说明 | 量级 | 在 loop_v1 里怎么验 | 前提 |
|---|---|---|---|---|
| **VRS (可变速率着色)** | Adreno / Mali 都支持, 接近免费的 shading 削减 | 中高 | `gpu_active_mean` + 画质对照 | **白盒** |
| **动态分辨率 + 手写上采样** (Snapdragon GSR / FSR1 / Arm ASR) | **纯 fragment shader, 不碰 NPU, 无格式往返、无张量拷贝。**1080p 量级通常在亚毫秒到 1 ms | 高 | `frame_p95` + 画质 | 白盒 (引擎侧), 部分引擎有开关 |
| TAAU / 时域累积 | 移动上要算 motion vector 的带宽账和 ghosting 的账 | 中 | 同上 | **白盒** |
| **NN 超分 / 插帧** | 见 §3 | 见 §3 | 见 §3 | **白盒 + NPU/GPU 卸载可行** |

### E. 时序 / 功耗 / 热 —— PC 上基本不存在

| 路线 | 说明 | 量级 | 在 loop_v1 里怎么验 | 前提 |
|---|---|---|---|---|
| **Frame pacing** (Swappy) | 稳定 16.6 ms 的体感远好于"平均更高但抖动" | 高 (体感) | **本机最可动的量: 抖动 p95−p50 = 2.66 ms** | 白盒为主 |
| **ADPF performance hint / DVFS** | 主动告诉系统这帧要多少, 避免频率震荡 | 中高 | `frame_p95` + 频率轨迹 | 白盒为主 |
| **热预算 / sustained fps** | **PC 上根本没这回事。手机的真 fps 是热稳态 fps** | 高 | loop_v1 已采热降频事件 (`n_thermal_events`) | **黑盒可做** ✅ |
| 系统限帧策略 / 可变刷新率 | 厂商策略层, 游戏设置里没有开关 | **决定性** (见 §4) | 已归因 | **黑盒可做 (需 root)** ✅ |

## 3. NN 超分 / 插帧: 单列一节, 附实测代价

把它单列不是因为它特殊, 是因为它是**全表里唯一需要 delegate 往返、唯一有张量拷贝**的一类,
账要算清楚才能和别的候选公平比较。

### 我们自己的实测

`src/bench.rs` 区分两个口径 (2026-09-09 NX809J 实测):

| 口径 | 含义 | gen10-6 实测 |
|---|---|---|
| `gpu` | GPU Delegate 内核总时延, 只含模型算子 | **2.967 ms** |
| `invoke` | 端到端 Invoke, 含 CPU↔GPU 张量拷贝与同步 | **比 `gpu` 高约 7 ms, 且与网络结构无关** |

540×960 → 1080×1920 时每帧拷贝量 **31 MB**。端到端 ≈ **10 ms**。

60 fps 的帧预算是 16.6 ms。**一个上采样 pass 吃掉 60% 帧预算, 这个形态在产品上是死的。**

### 但这 7 ms 的性质还没定论 —— 这是现在最该补的一个实验

那 7 ms 不一定是物理下限, 很可能有相当部分是**测量工装的产物**:

- `benchmark_model` 是从 **CPU 内存**喂张量的, 所以每帧都有一次 CPU↔GPU 往返;
  真接进引擎时, 帧**本来就在 GPU 显存里**, TFLite GPU delegate 支持直接绑 GL SSBO / texture,
  这趟往返可以整个省掉;
- 31 MB 里的大头是 1080p × RGBA × **fp32** 的输出; 换 fp16 / uint8 后是 8 MB 量级。

**这个实验一天能做完, 而它决定整条 NN 支线的去留。** 在这个数落地之前,
无论说"NN 不行"还是"NN 值得投", 都缺一块证据。建议作为 NN 方向的第一个动作。

### 机制上的一处更正

常见说法是"NPU 到 GPU 带宽不足"。更准确的描述是: 移动 SoC 上 **NPU 和 GPU 共用同一条 LPDDR,
没有独立的 NPU↔GPU 链路**。低分辨率帧写出去、NPU 读进来、放大后再写回、GPU 再合成 ——
问题不在缺专用链路, 而在这几次**往返**本身吃带宽和时延。

### NN 真正缺的对照组

现在 `sr_loop` 唯一的基线是 **Bicubic 37.286 dB**, 太弱。

应该补的对照是 **NN 超分 vs GSR / FSR1 / ASR** (§D 第二行那类纯 fragment shader 上采样器)。
一句提醒: 这类锐化型上采样器在 PSNR 上常常**输**给 NN 但观感更好, 所以这个对照不能只比 PSNR。

## 4. 黑盒 / 白盒: 这个分叉决定清单里哪些路线可做

`src/bench.rs` 的硬约束是**不侵入任何游戏进程**。对原神这类第三方黑盒游戏,
能动的只有系统级旋钮 —— render pass、shader、draw call **一个都改不了**。

| 目标 | harness 能干什么 | 对应上表 |
|---|---|---|
| **第三方游戏 (黑盒)** | 只能**评估**: 找到 gap、量化 gap, 改不了 | A 最后一行、E 后两行 |
| **自家 / 合作方引擎 (白盒)** | 上面整张表都开放, 但需要引擎侧 hook 与可重新打包的构建 | A–E 绝大部分 |

**本机黑盒实测的天花板**: 归因 5 轮结论一致 —— **限帧器封顶 @30 fps**。
帧周期 33.51 ms 贴着 30 fps 的 33.33 ms (±2%), 而 GPU 只用掉 **64.5%**, 余量 11.91 ms, 热事件 0。

含义很直接: **p50 被软件限帧钉死, 物理上降不下去。** 在这台机器的这个负载上,
上面任何降低 GPU 工作量的路线 —— 包括 NN 超分 —— **都换不出帧率**, 只能换功耗和热预算。

黑盒下还剩两个真实可动的量:

- **抖动** p95 − p50 = **2.66 ms** (对应 §E 的 frame pacing)
- **每帧 GPU 工作量** 21.61 ms (省功耗 / 热预算, 对应 §A、§C)

所以: **想验证 A–D 里的大多数路线, 必须拿到一个白盒靶子** (一个 Unity / 引擎 demo 工程就够)。
这是比买更多设备优先级更高的一件事。

## 5. harness 现在能观测到什么, 观测不到什么

诚实边界, 决定了上表里哪些"怎么验"是现在就能做的。

| 能看见 | 看不见 |
|---|---|
| 帧节奏 (p50/p95/p99/mean)、抖动 | **render pass / draw call 级归因** |
| GPU 执行时长与占比 (`gpu_active`, `gpu_share`) | 硬件计数器: 实测带宽、shader busy、tile 数、overdraw、纹理 cache miss |
| 总线投票与余量 (`bw_median`, `bus_vote_headroom`) | 顶点 / binning 的独立开销 |
| 队列等待 (`queue_p50`) | |
| 热降频事件、CPU/GPU 频率、结温 | |
| TFLite 算子级 GPU 内核延迟 (`bench`) | |

### 测帧手段的选型结论 (三条路都实测排除)

| 手段 | 结果 |
|---|---|
| `dumpsys SurfaceFlinger --latency` | **Android 16 上已失效**, 只回一行 vsync 周期, 没有逐帧数据 |
| `dumpsys gfxinfo <pkg>` | **测不到原神** —— 它走 SurfaceView, 绕开 HWUI。实测 48 秒内帧数停在 43 不动 |
| Perfetto `gpu.renderstages` / `gpu.counters` | **驱动未注册**。本机 91 个数据源里 GPU 相关只有 `android.gpu.memory` 和 surfaceflinger 那几个 |

最终走 **raw ftrace 的 kgsl 事件**: 纯文本、root 可开、不侵入游戏进程,
一次采集同时拿到帧节奏 + GPU 执行时长 + 带宽投票 + 热降频。

**这意味着 render pass 级归因在这台机器上做不到。** 结论是: 想要 §A/§B/§C 的细粒度归因,
要么换一台驱动注册了 GPU producer 的设备, 要么走白盒 —— 引擎侧自带的 profiler 标记比系统 tracing 更可靠。

## 6. 建议的下一步

按"能不能立刻验"排序:

1. **拿一个白盒靶子** (Unity / 引擎 demo 工程)。§4 说明: 没有它, A–D 的绝大多数路线连验都验不了,
   闭环只能反复验证同一个系统级旋钮。**这是当前最大的单点阻塞。**
2. **补那个 7 ms 实验** (GPU-resident 绑定 + fp16 对照)。一天, 给 NN 支线一个有数据的结论。
3. **鸿蒙侧接入**。目前全部结论都来自一台 Android 设备。`loop_v1` 的采集底层是 ftrace + kgsl,
   换到鸿蒙要重做这一层 (`hdc` + RenderService / hidumper), 上层判据逻辑可平移。
4. **黑盒线上把 frame pacing 做掉** (§E 第一行)。本机唯一还有余量的量是 2.66 ms 抖动, 其余都被限帧钉死。
5. **给 NN 补 GSR / FSR1 / ASR 对照组** (§3 末)。现有 Bicubic 基线不足以支撑任何取舍结论。

每条候选都走同一套流程: 基线 → 归因 → 改动 → 对照 → 统计判定 → 回滚 → 证据归档。
判定规则在看到候选数据**之前**落盘冻结。
