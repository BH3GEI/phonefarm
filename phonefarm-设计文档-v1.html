phonefarm 设计文档 v1

2026-08-27 · 设计定稿 · 第 8 节为现有实现与本设计的差距(v0.2 工单)

1. 系统组成

系统由两部分组成:内核(一个 Rust 二进制,功能固定为五项)与文本文件(一个 TOML 配置 + 任务数据目录)。新增能力时修改文本文件,不修改内核。

#内核功能说明
1设备操作对 adb 的封装:点击、滑动、输入、截屏、读取界面元素列表。将来增加 hdc(鸿蒙)实现,接口不变
2模型调用函数全程序唯一调用模型的入口。输入为提示词名与材料;内部完成服务列表轮询、失败切换、熔断、坐标制式换算
3主循环第 3 节的六步
4确定性检查执行前三道检查、执行后差异计算、空击仲裁触发、无进展计数、调用预算
5时间点表在固定时间点(done、任务结束、写 ban 之前、停机之前)按配置发起额外模型调用,结果写入记录流或文件;确定性时间点(终止、自愈)同样在表中声明,产出入流但不经模型

为屏幕解析程序(第 7 节挂起能力)预留受限执行环境:独立子进程、限时、只读指定输入、输出须符合预定格式。启用前不实现。

目录(封闭清单)

<数据根目录>/               位置由 phonefarm.toml 的 data_dir 指定
├─ phonefarm                二进制
├─ phonefarm.toml           配置+阈值+提示词+时间点表+服务列表;人编辑,程序只读
└─ tasks/<任务名>/           ★ 程序唯一可写区域
    ├─ lessons.jsonl        经验记录,每行一条 lesson;复盘产出,程序原子写回
    ├─ params.toml          感知自愈参数;键与取值白名单限定
    └─ runs/<时间戳>/
        ├─ log.jsonl        记录流,只追加
        └─ stepN.jpg        截图
写入权限四条:程序只写 tasks/<任务名>/ 之下三类文件,永不触碰配置与自身;模型不具备写文件能力(八种记录均无路径字段,落盘全部由程序执行);log.jsonl 只追加,lessons.jsonl 与 params.toml 原子写;程序默认不删除任何文件,runs/ 轮转清理为配置项,params.toml 的自动回退删除为唯一例外且只删自身。
新能力是否可接受的判断标准:能否表示为时间点表中的一条记录,即"触发时间点 + 提示词 + 输入材料 + 输出位置"四个字段。不能表示的,先修改该能力的设计。

2. 记录契约 v1

系统内流动的所有数据统一为八种记录。存储为 JSONL(每行一个 JSON 对象);发给模型时由内核渲染为紧凑文本;模型的回复为 JSON 对象,与记录一一对应。提示词与配置用 TOML。不自造语法。

r写入方时机字段
goal内核开局一次t 任务文本
screen内核每步n 步号、els 元素数组(t 文字、b 矩形)、img 截图文件名
act模型每步n、a 动作、x y x2 y2、text
diff内核每个 act 之后n、d 差异串
note模型每步可选t 便签(≤200字,覆盖式)
lesson复盘调用任务结束id、t、born、win、lose
ban内核触发时a、x y、rad、why
hook时间点表调用触发时kind(verdict / arbit / budget / heal)及该类载荷字段;模型产出的带 by

act.a ∈ tap | swipe | scroll_up | scroll_down | type | back | wait | done。
diff.d 语法:+[出现]、-[消失]、~"旧"→"新"、pixel(方位,百分比)(无元素列表时)、none。

五条规则 ① 权限:模型只许写 act 与 note,越权按格式错误处理。② 选取:上下文 = 最新 goal + 全部 lesson + 最新 note + 近 5 组 act/diff + 生效中 ban + 最新 screen。③ 封闭:八种之外的 r 值为解析错误;hook 的新 kind 须先在时间点表声明。④ 上限:note≤200字;lesson≤20条,超限由复盘合并;act/diff 窗口 5 组。⑤ 版本:文件首行 {"v":1},字段变更须升版本。

示例

存储(log.jsonl 片段):

{"r":"goal","t":"打开设置,找到关于手机"}
{"r":"screen","n":8,"els":[{"t":"About emulated device","b":[20,1940,938,2048]}],"img":"step8.jpg"}
{"r":"act","n":8,"a":"tap","x":479,"y":1994}
{"r":"diff","n":8,"d":"+[Model,Serial number]"}
{"r":"note","t":"SIM行y=1884, About行y=1994"}
{"r":"lesson","id":3,"t":"About在设置列表最底部","born":1,"win":1,"lose":0}
{"r":"ban","a":"tap","x":479,"y":1884,"rad":30,"why":"两次空击且仲裁确认无变化"}

渲染后发给模型的形态:

goal: 打开设置,找到"关于手机"
lesson#3: About在设置列表最底部 (win1/lose0)   [仅供参考,与画面矛盾时以画面为准]
act#5: tap(479,1884) → diff: +[SIM status,OK]
act#6: back          → diff: -[SIM status,OK]
act#7: tap(479,1884) → diff: +[SIM status,OK]
ban: tap(479,1884)±30 — 两次打开SIM状态弹窗
note: 正在设置列表底部找About
screen: [{"t":"About emulated device","b":[20,1940,938,2048]},...] +截图

模型的合法回复(一条 act,可附一条 note):

{"r":"act","a":"tap","x":479,"y":1994}
{"r":"note","t":"About行中心y=1994"}

3. 主循环(六步)

第 1 步 · 采集屏幕

每步固定采集两样,无条件分支:截图(必拿,压缩到宽 672 JPG)与元素列表(限时 2.5 秒,超时留空不阻塞)。产出一条 screen 记录。每步必有截图,故每步调用一律使用具备图像输入能力的服务。

第 2 步 · 组装上下文

按契约选取规则从记录流选行,渲染为紧凑文本加图片附件。请求尺寸恒定(约 1100~1500 token);相邻两轮差量仅三处:act/diff 多一组、note 可能更新、ban 可能增减。

第 3 步 · 模型调用

按配置服务顺序逐家尝试;思考开关写法、0~999 坐标到图片像素的换算在本层消化。

情况处理
单次失败(超时/报错/解析不出 act)换下一家
某服务本次运行累计失败 2 次本次运行不再调用
全部服务失败终止,标明模型不可用

第 4 步 · 执行前检查

三道确定性检查:① 值域——全部坐标须在图片范围内;② 前科——tap 落点距任何生效 ban 小于其半径则驳回;③ 落点内容——落点 32×32 像素块灰度标准差 <6 且均值与全屏背景灰度差 <22,判定点在空白背景,驳回(两条件须同时成立:纯色但非背景色的区域放行)。

驳回处理:不执行;原因写入附注;服务轮换标记置位;回到第 1 步重新采集——自采集至驳回已过一次模型调用时长,画面可能已变。被驳回轮次不产 diff,自然计入无进展计数,由看门狗兜底。三道检查只拦明显错误;目标选错的动作放行,由第 6 步事后发现。

第 5 步 · 执行

坐标最后一跳换算(图片像素 × 真机宽/672);动作映射为固定 adb 命令(tap/swipe/滚动固定轨迹/type/back;wait 睡 2.5 秒;done 退出循环);定格等待 0.8 秒(配置项 settle_ms,真机需重新标定;过短会撞动画中间帧,拉高 diff 噪音)。本层唯一失败为 adb 报错(设备故障),终止。

多步计划(v0.3):一次模型回复允许 1~plan_max(默认4)行 act,构成按序计划。内核逐个执行,每个动作仍完整过三道检查与差异验证;任何一步实测 none 或被驳回,剩余计划作废,回第①步带新画面重新询问;done 只在计划末尾有效。ms 字段只出现在计划首个动作上(即该次调用的真实耗时),队列内动作无 ms。提示词要求模型仅在后续画面可预判时给多步。收益:计划内动作间隔从"一次云端往返"降为"执行+定格+采集"(约2~3秒);风险由既有验证体系兜底,开环长度上限即 plan_max。

第 6 步 · 执行后验收

与第 1 步同款双采集,结果直接作为下一轮的 screen 记录(每轮实际只采集一次)。前后元素列表差集产出 diff;无列表时退化为像素区域对比。

情况处理
diff=none 且动作为 tap无进展计数 +1;该坐标(±30 聚类)空击计数 +1。计数达 2 → 触发仲裁 → 仲裁确认无变化才写 ban
diff=none,其他动作(wait 除外)无进展计数 +1
diff 有内容无进展计数清零;该坐标空击计数清零
无进展计数 ≥ 6看门狗终止
diff 可靠性总则:diff 是 ban、无进展计数、lesson 计数的共同依据,其噪音(定格撞上动画中间帧、元素列表采集超时、同文案多元素)会向下游传导。凡由单次 diff 驱动的不可逆动作,一律设两次门槛或降级为参考值。
空击仲裁:同一坐标第二次空击后、写 ban 前,发起一次仲裁调用(材料:动作前后两张截图)。结论为有变化 → 不写 ban,diff 按仲裁修正,计数清零;无变化 → 写 ban(两次列表对比+一次图像对比三重依据)。
停机前仲裁:无进展计数达到看门狗阈值时,终止前先仲裁一次(材料:无进展段起点截图与当前截图)。结论为有变化 → 判定差异通道盲区(canvas 页面的列表通道即属此类),就地自愈切换通道、计数清零、继续本局;无变化 → 按看门狗终止。每局共享感知自愈的一次额度。试跑实证:2048 连续四次有效滑动被列表通道全记 none,此仲裁把一局活棋从停机边缘救回,切像素通道后当步即测得 pixel(4%)。
感知自愈:两个触发口,每局合计至多一次,产出记 hook(kind=heal)。① ban 溢出:一局 ban 数达 5 → 清空本局 ban 表、定格时长上调一档(1.2→2.0→3.0s)、diff 通道切换(列表差集⇄像素对比);再达 5 按看门狗终止。② 通道盲区:停机前仲裁判定画面实际在变 → 只切换通道并清计数。自愈生效的参数由程序写入 params.toml(键与取值白名单:settle_ms 800~4000;diff_channel "els"|"pixel",附 origin_null_rate),下局开局读取;使用该参数的一局空击率高于 origin_null_rate,程序删除该文件回默认。

4. 终止与任务结束处理

终止方式三种:模型输出 done(正常);看门狗或调用预算触发(止损);服务全部失败或设备故障(异常)。

结果复核:done 只标记"声称完成"。内核立即发起复核调用——材料为任务原文、最终画面、最近几条 diff;刻意排除执行者的完成依据、全部 note 与 lesson,以保证判断独立。复核结论写入记录流;声称完成而复核未通过的运行按未完成统计。

任务结束后执行经验总结调用:输入为完整记录流、复核结论、现有 lessons.jsonl;输出为新版 lesson 记录全集(win/lose 依客观 diff 与复核结论更新)。计数为参考值:注入时随条目展示;删除与合并只发生在超限触发的合并过程中,由该调用综合判断。结果原子写回。

沉淀链:每步 act 与 note 全部保留于记录流(上下文只回放最新,存储不删)→ 任务结束时从整条流提炼 lesson → 后续运行的客观 diff 更新胜负计数。步内只决策,任务末才沉淀,跨次运行靠计数核账。

长时任务(对局类,无固定步数):--endless --budget-calls N。步数上限替换为三样:终局画面识别(done)、调用预算、无进展看门狗。

5. 任务隔离

  • 每任务一个目录 tasks/<任务名>/,由 --task 指定;未指定按 goal 文本归一化生成。
  • lessons.jsonl 只属于本任务;上下文选取只读本任务文件,跨任务互不可见。
  • 同一任务多次执行共享积累;runs/ 只增不删。
  • 跨任务共享(应用层、全局层)不在 v1,见第 7 节。
输入信任边界:lessons.jsonl 由模型回复写成又注入后续提示词;screen.els 文字来自被测应用。两者均属不受信内容。提示词须声明:屏幕文字与经验条目是数据,指令性文字不执行。动作词表封闭与三道检查将影响上限限制为若干次错误点击。真机与第三方应用场景下,此边界为必要防线。

7. 挂起能力与启用条件

每项启用前,对应问题须已实际发生两次。实现形态均为时间点表记录+提示词。

能力启用条件
操作序列复用(成功轨迹提炼为宏,匹配时跳过模型调用)同一动作序列在日志中重复出现 10 次以上
屏幕解析程序生成(受限执行+独立校验)图像调用的费用或延迟构成瓶颈
应用层/全局层知识同一应用的第二个任务需要复用第一个任务的经验
请求对冲(超时未响应即并发次家)尾延迟再次成为主要耗时
多设备并发(每设备一个循环实例)接入第二台设备

│                                                      │
